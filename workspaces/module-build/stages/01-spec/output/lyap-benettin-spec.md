# Spec: lyap-benettin

Library layer: Lyapunov (`_config/architecture.md`, "Module map" row Lyapunov). Branch m2-p1-modules. Status: approved at the Batch B 01-spec checkpoint (D30). Float32 is out of M2 (decision D24); every tolerance below is in units of eps(T) for T in {Float64, Double64} and BigFloat(256) for oracle runs. Double64 uses its effective epsilon 2^-100 (precision spec, Amendments), not 2^-104. This spec also holds the definitions shared by all five Batch B specs (section Equations, S1 to S8); the other specs point here and do not repeat them. Spec-local open points are labelled P1 to P4; the owner's answers to the Batch B review are decision D30, cited as (D30), not to these.

## Scope

- Catalog row L1 (`_config/catalogs/lyapunov.md`, section A): finite-time maximal exponent by single-vector renormalization, X(n) at every handoff. Milestone row M2 of `_config/build-order.md` (all nine modules must be verified).
- Prerequisites (Batch A, stage 04 reports in `workspaces/module-build/stages/04-verify/output/`; catalog Status flips at stage 05): tangent-core (stream, handoff interval tau, per-orbit summary contract, health errors, compensated sums, Amendment D28 for a state longer than the tangent dimension), standard-map (Y1, Y5, wrapped system with counts), precision (element types), diagnostics (det and symplecticity residuals). Cited below as "tangent-core spec item", "standard-map spec item", and so on.
- The module is a reducer on the tangent-core stream with k = 1. It reads the deviation vector at each handoff, accumulates the log of its norm, and replaces the vector by the unit vector (tangent-core spec, Equations E7). It never changes the orbit.
- Diagnostics applicability (diagnostics spec, Scope): the det and symplecticity residuals are chained in; pairing, sum and orthogonality loss are not defined for one vector and are not reported here.
- Out of scope: classification thresholds (pre-registered per study, `_config/numerics-policy.md`), the stopping rule X1m of Skokos2010 Table 1 (a study concern), stretching numbers and FTLE fields (L13, L14, M4), flows (M5), more than one vector.
- Inherited from Batch A (decision D27), taken over as criteria AC13, AC14 and AC12: tangent-core 04 log lines ORACLE-CT1 and ORACLE-CT2 (DEFERRED); diagnostics 04 log line AC7 (DEFERRED, external full-spectrum sum next to eps_sum; moved to lyap-gram-schmidt as recorded line R3, (D30)); precision spec Oracle (Benettin at Float64, Double64, BigFloat with an external-package cross-check). The external package is named in the Oracle section.
- Keys: no `numerics-defaults.toml` key is proposed. tau stays `renorm_interval_tau`; for k = 1 only the overflow bound of the tangent-core spec (Algorithm, "Proposed renorm_interval_tau", item 3) limits an override.

### Shared definitions for Batch B (S1 to S8)

- S1 Conventions (single home; GS, HH, SVD and L2 point here). n counts map steps; handoffs at n = j tau; logs are natural; exponents are per map iteration (as the benchmarks rows). X(n) is the L1 series; lambda_1(n) of other estimators is the same quantity. Symbols, one meaning each across Batch B: M_state = max(1, abs(K), largest coordinate magnitude) is the state magnitude of the precision-spec rounding model (wrapped mode: M_state <= max(1, abs(K), 2 pi)); it is renamed from M_n, which collided with the one-step tangent M_n of E1 and with M_max (largest tangent entry) of diagnostics, GS and HH; the undefined "tp" of the earlier text is dropped. G_first (S3, renamed from G_1) is the squared Frobenius norm of the first-window product; for a determinant-one 2 x 2 window G_first = G + 1/G. G without index is the singular-value ratio of diagnostics B4; G_w is GS G10.
- S2 Identical orbit. Two estimators are compared "on the identical orbit" when they use the same system and K, the same initial point (a Float64 draw widened exactly, precision spec Algorithm 2), the same initial deviation basis (tangent-core spec, "Initial deviation vectors", first k columns), the same tau, element type, state mode and run seed. The stream advances the orbit independently of every reducer (reducers may replace only the deviation matrix, tangent-core spec Algorithm, Contract), so the orbit points are bitwise equal across estimators and comparisons on one orbit are pathwise at any n. They are not restricted by the orbit horizon n_H of the precision spec; that horizon applies only when the orbits themselves are computed in different arithmetic. This is the single protocol: the other specs write "identical orbit as L1 S2". It uses the property that column j of the seeded initial frame does not depend on k, which the tangent-core spec does not yet state (correction proposed in the review, (D30)); for lyap-two-trajectory the independence of the orbit from the reducer holds under the contract choice of that spec (D30).
- S3 Same-orbit rounding bound for the sum of ln stretch of one unit vector (derived, first order, proposal). Let P_1 be the tangent product over the first window and G_first = squared Frobenius norm of P_1. Define B_S(n) = 8 eps(T) (n + G_first), a bound on |computed n X(n) - ln(norm of Y_n w_0 / norm of w_0)|, the reference being the BigFloat(256) product of E2 evaluated at the realized orbit points. Basis: each handoff contributes a relative rounding error of a few eps (a matrix-vector product, a norm, a division, a compensated add: tangent-core spec, Accumulated logarithms) and the n terms add; after the first window the vector lies near the expanding direction, so a rounding error in the contracting direction does not change the norm to first order; only the first window can be amplified, by at most G_first (the squared Frobenius norm bounds the ratio of largest to smallest singular value of a determinant-one 2 x 2 matrix, derived). The factor 8 follows tangent-core spec AC2 (a). Stage 04 reports the realized ratio; the owner may tighten c = 8. Home for i = 1: the QR-family specs use the single unit theta_sum (GS G13) for all i, which is intentionally looser than B_S/n for i = 1; the k = 1 relation to this bound is tested at GS AC10 and HH AC8(a).
- S4 Cross-method relations on the identical orbit (derived). (a) QR family: if the first column of the initial basis is w_0, the first replaced column is the normalized first evolved column, so the sum over windows of ln R_11 equals n X(n) in exact arithmetic; computed series differ by at most (B_S^A(n) + B_S^B(n))/n in exponent units (the pair bound used by GS AC10 and HH AC8(a); exact identity: GS G7 with p = 1). (b) Stabilized SVD: GS G8 with p = 1 (sandwich of the QR exponent below the singular-value exponent); for d = 2 the sharper lyap-svd-stabilized V7. (c) Two-trajectory: pathwise bound in the lyap-two-trajectory spec.
- S5 Statistical comparison rule. Two estimators on N_A and N_B independent seeded orbits agree when the difference of the ensemble means of X(n) is at most 4 sqrt(s_A^2/N_A + s_B^2/N_B), s the sample standard deviation over orbits (the "4 combined standard errors" of the tangent-core oracle). Single home of the rule: GS, HH, SVD and L2 cite S5.
- S6 CPU vs GPU: no tolerance is defined in the Batch B specs. The single home is tangent-core spec AC12 (regular class K = 0.5, chaotic class K = 10, ensemble sizes, n and the numeric tolerances are stated there); every Batch B CPU-vs-GPU criterion points to it, on S/n never on trajectories (risk K16), with the regular-class screening of S7 added (D30). The label S6 is kept so that references stay valid.
- S7 Panel and starts. K in {0 (analytic), 0.5 (regular class), 0.9716354 (golden-mean K_c, benchmarks row "Golden-mean KAM torus breakup", as a panel value only), 2, 5, 2 pi, 10}. Starts: x, p uniform in [0, 2 pi) as Float64, run seed from `numerics-defaults.toml`, orbit ids 1..N. "Regular class at K = 0.5" means a start whose L1 value X(1e5) is at most 5e-4; seeded starts failing this (thin chaotic layer) are replaced by the next orbit id and counted in the report. S7 is the single home for panel, starts and screening: every Batch B criterion that uses the K = 0.5 regular class applies this screening, and the other specs cite S7.
- S8 Retained outputs (`_config/research-question.md`, "Outputs retained"): the series X(n) at every handoff (storage schedule chosen by the caller), the final sum and compensation term, the det residual series of diagnostics. Not a final scalar only.

## Algorithm

Per orbit, after the tangent-core stream's step n = j tau (handoff j):
1. Read the evolved deviation vector (d = 2 rows, one column; tangent-core spec Amendment D28 A2). Compute alpha_j = Euclidean norm, evaluated so that it neither overflows nor underflows for any finite vector of the element type (scaled evaluation; a plain sum of squares overflows at half the exponent range, which would halve the usable tau bound of the tangent-core spec).
2. If alpha_j is zero or not finite, raise a numerical health error naming the deviation matrix, with orbit id and handoff step (tangent-core spec, Numerical health; the finiteness check there does not catch a zero norm).
3. Add ln alpha_j to the compensated running sum (tangent-core spec, Accumulated logarithms). Emit X(j tau) = sum / (j tau).
4. Replace the vector by the unit vector (E8).

Initial vector: the seeded unit vector of the stream (E4: almost every start gives chi_1). tau: recorded run parameter, default 1; a study sweeps it within the overflow bound. Wrapped state with winding counts (decision D28): the tangent depends on x only through cos x, so the estimator reads only the deviation matrix and needs no change for state length greater than d. The Y5 maps are used as given.

## Invariants

- I1 Replacement transparency (E8): X(n) at a common n is independent of tau in exact arithmetic.
- I2 Every alpha_j is finite and positive. For the standard map alpha_j lies in [sigma(K)^(-tau), sigma(K)^tau] (E14).
- I3 The orbit is unchanged by the estimator (S2).
- I4 Orbit independence: orbit j's series depends only on (system, parameters, initial point, seed, j, tau, N, T, state mode); not on threads, chunk, position in the ensemble; across backends only to S6.
- I5 Additivity: n X(n) is a sum over handoffs, so the series at handoff j is the series at handoff j-1 plus one term.
- I6 Hot loop allocates nothing after warm-up (BigFloat excepted, precision spec Compute).

## Compute

Policy `_config/architecture.md`, "Compute" (D17, D25); owner decision, M2 kickoff: Double64 is the extended type, BigFloat CPU-only. The estimator is per-orbit and data-parallel, fused into the stream's single kernel; the reducer state (sum and compensation term) is already counted in the tangent-core memory formula M(s, d, k, T) = sizeof(T)(s + d k + 2k) + 16, so L1 adds 0 bytes; with k = 1: 64 bytes (s = d = 2, Float64), 80 bytes (s = 4, Float64), 112 bytes (s = 2, Double64). Diagnostics adds its own reducer state (diagnostics spec, Compute). The retained series goes to caller-provided storage. GPU candidate for Float64 and Double64 (isbits, one scaled norm and one log per handoff); the Double64 log and norm must compile for the device or the run falls back with the recorded reason "kernel does not compile for the element type". BigFloat: CPU only, same reason on a GPU request. No LAPACK, so no "reducer is CPU-only" fallback. GTX 1050, cc 6.1, weak Float64 (risk K15); GPU is the default for T only after the tangent-core benchmark (AC13 there) shows a win. CPU-vs-GPU agreement: S6. CI has no GPU: the kernel runs on the CPU backend.

## Oracle

Package test suite (analytic, invariant, cross-method, small self-contained; D21): E10 to E13 closed forms; BigFloat(256) products at realized orbit points (n <= 1e4, no external package); full BigFloat orbit for short regular runs; tau invariance; health; norm scaling; thread invariance.

Separate verification environment `verify/`, driven from stage 04 (D21, D27): ChaosTools, in the installed source read 2026-10-13 (`~/.julia/packages/ChaosTools/0SbsT/src/chaosdetection/lyapunovs/`). Finding for the owner: ChaosTools `lyapunov` is the two-trajectory method (nearby orbit rescaled, cites Benettin1976; defaults d0 = 1e-9, rescale only when the distance leaves [1e-3 d0, 1e3 d0]), not tangent integration, so the tangent-core wording "ChaosTools tangent integration (lyapunov, lyapunovspectrum)" is corrected here: the tangent oracle for L1 is `lyapunovspectrum` (QR of the tangent deviation vectors at every step, first exponent), run with k = 1; `lyapunov` is the oracle of lyap-two-trajectory. `lyapunovspectrum` takes a user-built tangent system with user-supplied initial deviation vectors and a hand-coded Jacobian (read in the installed source, not yet run), so ChaosTools can start from the identical seeded w_0 (contrary to the tangent-core spec Oracle, which assumed it could not (D30)); AC13 uses this for a pathwise line next to the inherited loose one. This paragraph is the single home of the ChaosTools facts for all Batch B specs, which point here and use the lifted rule stated next. The standard-map rule in ChaosTools wraps both variables each step (standard-map 04 report, Criterion 19: identity conversion); for tangent runs the orbit is unaffected by the wrap, but the oracle rule used in AC13 to AC15 is the lifted form so the orbit points match the lifted stream. Also in `verify/`: BigFloat(256) vs Float64 vs Double64 comparisons over long runs, and the GPU comparison.
Loose sanity lines (reported, never pass/fail, K18): benchmarks rows "Lyapunov exponent, single chaotic orbit" (0.298 at K = pi/2; 1.172 at K = 2 pi, converted by E9) and "Standard map largest Lyapunov exponent, large K" (ln(K/2); Shevchenko2014 form ln(K/2) + 1/K^2 for K >= 4.4), compared with X(1e6) ensemble means at K = pi/2, 2 pi, 10.
