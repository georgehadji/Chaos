## Design

- Workspace (Surface 1 of the test plan, as written). Layout `max(m, 1) x chunk` `UInt32` matrix, one orbit per column (orbit-major). The kernel passes `view(ws, :, i)` to `_orbit_body`; the first launch (`n0 == 0`) zeroes it with an explicit loop; later launches read the carried contents like the state. `propagate_orbit` zeroes the caller's workspace before the first step, so a stale workspace is harmless; with `workspace = nothing` it allocates `zeros(UInt32, m)`, or uses the shared empty constant `_NO_WS` when the chain asks for nothing (no allocation for the existing callers). `_orbit_body` takes `ws` as an optional last positional argument, so the call sites that the tangent-core AC14 audit counts (and the Experiments callers, which pass nine arguments) are textually unchanged.
- Chain rule: `_chain_workspace` sums the requests and throws `ArgumentError("at most one reducer of a chain may request a workspace ...")` when more than one is nonzero; `propagate` calls it before any work, `propagate_orbit` before the first step. The whole orbit vector goes to every `reducer_step` of the chain; reducers with the default methods ignore it.
- Memory formula: `rbytes = (isbits tuple ? sizeof(s0) : 0) + 4 * mws`, so a chain without a workspace has the same chunk size as before (the tuple `sizeof` is kept, not the sum of per-reducer sizes, to stay bitwise with the tangent-core device test). `reducer_bytes(r, T, v, k)` is the per-reducer form.
- Existing reducers: no existing method changed. The new generic methods forward (`reducer_step(...ws)` to the five-argument form, `reducer_update(...ws)` likewise, `reducer_final(r, st, ws)` to the two-argument form, `reducer_workspace` is 0). The suites of all other modules are green and their orbit outputs bitwise unchanged.
- `StretchState` (isbits): four `CompensatedSum` (log sums and sums of squares, per column), the failure record (value, step, code, column), `n`, `K`. 104 bytes in Float64 and 176 in Double64 (inside the 80 to 112 and 144 to 192 windows of the plan, Item 4); reducer bytes 920 / 992 at B = 100 and 8120 / 8192 at B = 1000. The log sums use the operations of MEGNO, so they are bitwise those of L1, SALI, FLI and MEGNO (AC4 passes bitwise). `tau` is recovered as `n / K` (K counts successful handoffs).
- Cell index: `spectrum_cell` is the one function (reducer and tests). `floor(Int, ::Double64)` is replaced by `floor(Int, x.hi)` corrected by the sign of `x.lo` only when `x.hi` is an exact integer (the high part is either an integer or at least an ulp from the next one while `abs(lo)` is at most half an ulp), so the hot loop allocates 0 bytes (AC12c passes for both types and both chains). The increment of the count is bounds-checked (no `@inbounds`): a reducer run through a path that supplies no workspace (the nine-argument `_orbit_body` of Experiments) raises a `BoundsError` instead of writing out of bounds.
- D: `spectral_distance` accumulates the squared differences and the totals as `Int`, converts the sum into the element type exactly (`exact(T, S)` above 2^53, because `Double64(::Int)` goes through Float64), `sqrt(S) / (k sqrt(h))`. The final computes `h = (T(hi) - T(lo)) / B` in the element type; the tests compare `D` bitwise with the pure function of the same `h`.
- `stretching_range` computes the bound at 256 bits from the stored `K` (or the stored 2 x 2 matrix: `sigma_max^2 = (F + sqrt(F^2 - 4 det^2)) / 2`, `F` the squared Frobenius norm), pads by `8 effective_eps(T)` relative, and rounds once into `T`: the padded value is 7.5 to 8.5 eps above the exact bound, inside the 4 to 16 eps window for both types.

## Deviations from the spec and the plan

1. `stretching_range(::LinearSymplecticMap)` is implemented for 2 x 2 matrices only (closed form of the largest singular value in BigFloat); a larger `LinearSymplecticMap` gives an `ArgumentError` asking for the range by hand. The spec criteria use `d = 2` only (Y5); a 4D linear map would need a BigFloat symmetric eigenvalue routine, which the package does not have. The "no stretching" test is `ln sigma_max <= 8 eps(T)` (a rotation block has `sigma_max = 1` up to its own roundoff, which must read as no stretching).
2. `min_per_cell < 0` is an `ArgumentError` (not in the spec; the flag would be meaningless). `range` entries may be integers (converted to `Float64`).
3. The workspace matrix has at least one row even when the chain asks for nothing (avoids a zero-row device array; the plan lists a zero-row matrix as unknown for CUDA.jl). Reducers that ask for nothing never see more than that unused row.
4. The test plan names the bench `bench/stretching-numbers.jl`; the task file name `bench/stretching.jl` is used (as `bench/rli.jl`).
5. `reducer_update` has no five-argument method for `StretchingNumbers` (a direct five-argument call is a `MethodError`; the reducer is only meaningful with its workspace).

## Performance (bench/stretching.jl, BenchmarkTools, median, 3 s per benchmark)

Measured with `--check-bounds=yes` (the only flag set whose caches load here), which makes every bounds check real and favours no reducer; absolute numbers are therefore pessimistic, ratios are indicative. Windows timer resolution is 100 ns, so the per-step rows are not usable; the orbit rows are.

| Run (1000 steps of the wrapped standard map, K = 6, tau = 1) | Time | Ratio to StretchingNumbers B = 1000 |
|----|----|----|
| L1 (`Benettin`, one column) | 78.6 us | 0.94 |
| MEGNO (two columns, five sums per column) | 96.4 us | 1.15 |
| RLI (pair, 4D product map) | 127.8 us | 1.53 |
| StretchingNumbers, B = 100 | 69.1 us | 0.83 |
| StretchingNumbers, B = 1000 | 83.7 us | 1.00 |
| chain {StretchingNumbers (reader), MEGNO} | 161.4 us | 1.93 |
| `propagate`, 1024 orbits x 1000 steps: SN B = 1000, MEGNO | 121.6 ms, 144.9 ms | 1.00, 1.19 |

So the cost of the two-column histogram stream is about the cost of L1 (+6 percent) and below MEGNO; the two scattered 4-byte increments per handoff are negligible on the CPU (B = 1000 is 21 percent above B = 100, the difference of cache footprint). The evaluation of D (O(B), 3.4 us with the count copy at B = 1000, once per interval of 100 steps) adds about 0.03 us per step. The GPU cost (record R6 on the GTX 1050) is not measurable here.

## Known limits and things not done or not verifiable here

- GPU: the CUDA extension change is mechanical (one extra `KernelAbstractions.allocate(b, UInt32, 1, 1)` and the argument in the `_orbit_kernel!` call of `compiles(T)`) and has not been compiled or run: there is no GPU in this session. Whether `view(ws, :, i)` of a `CuDeviceMatrix`, the explicit zeroing loop and the `UInt32` increment compile for B near 1000, whether the orbit-major layout is acceptable (a chunk-major layout would coalesce neighbouring threads' increments better and would change only `_alloc_bufs` and the view), and the GPU speed relative to the stream are for criterion 16 and `verify/gpu.jl` at stage 04. If the kernel does not compile, the recorded fallback "kernel does not compile for the element type" applies and the run goes to the CPU.
- Experiments: its device path and recorder call `Tangent._orbit_body` with nine arguments and allocate no workspace, so a chain with `StretchingNumbers` is not supported there until the Experiments recorder allocates and reads the workspace (obligation for stage 05; with the bounds-checked increment a misuse is a `BoundsError`, not silent corruption). `propagate` finals hold a `(B + 2) x 2` count matrix per orbit (8 kB at B = 1000; Item 9 of the plan): at 10^6 orbits that is 8 GB on the host, so the recorder must consume chunk by chunk.
- Counts are `UInt32`: valid to 4.29e9 handoffs; `check_run` limits a run to 10^9 handoffs and the caller must call it (the reducer cannot see `tau` or `N`). The interval is validated and recorded only; D is read by `reducer_final(r, st, ws)` at the evaluation handoffs (probe or recorder).
- `stretching_range`: 2 x 2 linear maps only (Deviation 1).
- The reducer needs the caller's range; `StretchingNumbers(; range = stretching_range(sys))` is the standard use. A narrower range counts the excess in the overflow cells, which are part of D.
- The hot loop was checked to allocate 0 bytes on the CPU (AC12c). The `propagate` path allocates per chunk only (buffers, finals).
- Not done (stage 04 / 05): criteria 14 to 16, R1 to R7, the `verify/stretching-numbers.jl` script, the Experiments obligations, the catalog status.
